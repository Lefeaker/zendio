# Connection testing

The Options connection button checks the configured channels without creating a note. REST success means the service answered with the official Local REST API root status and accepted the supplied API key. It does not prove a subsequent note or attachment write, filesystem permission, or the configured Vault name matches the open Obsidian Vault.

A reachable HTTP 200 alone is insufficient: the root endpoint also answers unauthenticated callers. Zendio requires a successful HTTP response containing JSON with `status: "OK"`, `service: "Obsidian Local REST API"`, and `authenticated: true`. HTML, malformed JSON, another service, and missing/false authentication fail. Additional response fields remain optional. This common signature is verified in the official [2.0.0 implementation](https://github.com/coddingtonbear/obsidian-local-rest-api/blob/2.0.0/src/requestHandler.ts), [3.2.0 implementation](https://github.com/coddingtonbear/obsidian-local-rest-api/blob/3.2.0/src/requestHandler.ts), and [current OpenAPI root contract](https://github.com/coddingtonbear/obsidian-local-rest-api/blob/master/docs/openapi.yaml). It deliberately does not require newer manifest, certificate, extension, or state metadata.

Each HTTP probe has a ten-second budget covering response headers and body consumption. Each default/per-Vault pipeline has a twenty-second budget, including configuration loading, local-folder permission lookup and all candidates. The default test can continue to its next fallback candidate after a ten-second probe timeout while the overall budget remains; cancellation and the twenty-second deadline stop further attempts. Additional-Vault channel aggregation remains unchanged. The outer signal prevents later candidates from starting after expiry; both deadlines bound waiting even if a transport ignores abort. Local-folder-only additional Vaults retain their existing permission check and need no REST credentials.

Options bounds each message-channel wait at twenty-five seconds and clears that request's pending state when it settles. A timed-out response cannot complete a later request or clear its pending state. The mounted storage action uses its existing generation to reject earlier results after another test, a relevant Vault edit (including edit-and-revert), or disposal; it also compares tested configuration with the current draft to detect external replacement. Connection testing never commits or clears draft edits.

Regression coverage: `connectionTestRecovery.test.ts` exercises real default/per-Vault pipelines with transport faults; `connectionTester.test.ts` covers message timeout/retry/late reply; `productionStitchShell.actions.test.ts` covers mounted action intent. `optionsConnectionRecovery.browser.test.ts` uses an installed extension, the real Options button and an isolated loopback service for valid, unrelated, unauthenticated and stalled HTTP responses. Its message-fault test replaces only the browser message transport, leaving the production request and UI owners active. No personal Obsidian profile or API key is used.
